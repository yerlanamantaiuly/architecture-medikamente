# Задание 3. Data Encryption at Rest and In Transit

Стратегия защиты данных для целевой архитектуры «Медикаменте» (см. Task2): учёт состояния данных, класса чувствительности, профиля риска и средств контроля.

## 1. Классификация данных

### 1.1. По состоянию

| Состояние | Где встречается | Риск без защиты |
|-----------|-----------------|-----------------|
| **At Rest** | Postgres, object storage медкарт, backup, Data Lake (raw/curated), тома K8s, 1С DB, архивы | кража диска/бэкапа, доступ админа инфраструктуры к открытому тексту |
| **In Transit** | HTTPS клиент↔API, mTLS сервис↔сервис, Lab API, KKM/эквайринг, ETL в озеро, уведомления | MITM в сети филиала/интернета, перехват ПДн в интеграциях |
| **In Use** | память приложения, кэш, UI, логи, временные файлы | утечка через логи/дампы, XSS/IDOR в ЛК |

### 1.2. По чувствительности и профилю риска

| Класс | Примеры | Чувствительность | Профиль риска | Требование шифрования |
|-------|---------|------------------|---------------|------------------------|
| `public` | прайс, публичное описание услуг | низкая | репутация при порче целостности | transit (TLS) достаточно |
| `internal` | расписание кабинетов без ФИО, номенклатура ТМЦ | средняя | внутренняя утечка | rest: volume; transit: TLS |
| `pii` | ФИО, ДР, телефон, e-mail, адрес, договор | высокая | 152-ФЗ, репутация, штрафы | rest + transit; маскирование в UI/логах |
| `pii.special` | диагнозы, заключения, анализы, хронические заболевания | критическая | спецкатегория ПДн, максимальный ущерб | rest (отдельный ключ/HSM) + transit (mTLS) + field-level где возможно |
| `payment` | токены оплаты, чеки, связь платёж↔пациент | высокая | финансы + ПДн | rest + transit; токенизация PAN; сегмент payments |
| `secrets` | пароли, refresh-токены, ключи API | критическая | полный компромисс контура | только хеш/Vault; никогда в git/логах |
| `audit` | журналы доступа к ПДн | высокая | сокрытие инцидента при порче | rest (WORM/append-only) + transit; целостность (подпись/hash chain) |

### 1.3. Дополнительные параметры классификации

| Параметр | Значения | Влияние на защиту |
|----------|----------|-------------------|
| Владелец домена | clinical / CRM / billing / inventory / analytics | разные ключи KMS и политики доступа |
| Срок хранения (`retention`) | P1Y / P3Y / legal_hold | ротация ключей, crypto-shredding при удалении |
| Субъект | patient / employee | ABAC и маскирование |
| Назначение | operational / analytics / backup | для analytics — обезличивание вместо хранения открытых ПДн |

## 2. Обоснование необходимости защиты по классам

| Класс / данные | В чём необходимость защиты |
|----------------|----------------------------|
| `pii` (идентификация, контакты) | Прямая идентификация субъекта; утечка → нарушение 152-ФЗ, фишинг, потеря доверия при масштабировании филиалов |
| `pii.special` (клиника, анализы) | Спецкатегория; раскрытие диагнозов/анализов наносит максимальный вред пациенту и бренду; без усиленного шифрования и контроля доступа риск неприемлем |
| `payment` | Связка платежа с пациентом усиливает ущерб; двойной Excel-учёт As-Is расширял поверхность — в To-Be только защищённый платёжный контур |
| `secrets` | Компрометация учёток = обход RBAC/ABAC и доступ ко всем классам выше |
| `audit` | Без защищённого журнала нельзя расследовать инцидент и доказать факт доступа/отказа |
| `internal` / ТМЦ | Ниже риск по ПДн, но нужна целостность учёта и изоляция от clinical-контура |
| Backups всех классов | Копия = полная база; бэкап без шифрования обнуляет защиту at rest |

## 3. Базовые инструменты защиты

### 3.1. At Rest

| Инструмент | Применение |
|------------|------------|
| **Disk / volume encryption** (LUKS, cloud volume CMEK) | все тома БД и object storage |
| **Transparent Data Encryption (TDE)** / Postgres TDE-эквивалент + filesystem encryption | CRM, Lab results, Payments DB |
| **Field-level encryption** (приложение + KMS) | диагнозы, результаты анализов, поля `pii.special` |
| **Object storage SSE + bucket policy** | сканы договоров и клинические файлы; запрет public ACL |
| **Backup encryption** + отдельный ключ | PITR/снимки; доступ к ключу бэкапа — по процедуре |
| **Crypto-shredding** | удаление/прекращение обработки по запросу субъекта через уничтожение DEK |
| **Hash + salt / Argon2/bcrypt** | пароли сотрудников и пациентов ЛК |
| **Токенизация платежей** | PAN не хранится в CRM; только токен эквайера |

### 3.2. In Transit

| Инструмент | Применение |
|------------|------------|
| **TLS 1.2+** (предпочтительно 1.3) | Client/Staff Portal, мобильный ЛК ↔ API |
| **mTLS** | Lab Integration ↔ лаборатория; service mesh (внутри K8s) для clinical/payment |
| **VPN / private link** между филиалами и ЦОД/облаком | админский и репликационный трафик |
| **Отказ от открытого OLE/TCP для ПДн** | замена As-Is канала KKM→1С на TLS-интеграцию через Payment Gateway |
| **Certificate management** (cert-manager / PKI) | ротация сертификатов сервисов |
| **Запрет ПДн в URL и query-логах прокси** | API Gateway политики |

### 3.3. In Use (смежно, обязательно)

| Инструмент | Применение |
|------------|------------|
| Маскирование в UI по роли | кассир/ресепшен не видят полный clinical |
| Redaction ПДн в логах | app + gateway |
| Короткоживущие токены (OAuth2/OIDC) | ЛК и Staff Portal |
| Memory-safe handling секретов | Vault agent / CSI secrets |

## 4. Автоматизированный контроль

| Средство контроля | Что проверяет | Куда алертит |
|-------------------|---------------|--------------|
| **Policy-as-code** (OPA / Kyverno): запрет Deployment без TLS и без encrypted PVC | drift конфигурации | CI + runtime admission |
| **CI-сканер контрактов** (OpenAPI `x-data-class`) | снятие тега `pii*` / утечка полей в публичный API | блокировка merge |
| **DLP / сканер хранилищ** (регулярки ПДн в object storage и Data Lake raw) | незашифрованные/неразмеченные объекты | Security + Privacy |
| **CSPM / проверка bucket ACL** | публичные бакеты с `pii` | P1 alert |
| **Certificate expiry monitor** | просрочка TLS/mTLS | on-call |
| **Audit pipeline**: каждое read/write `pii` / `pii.special` | аномалии (массовое чтение, чужой `patient_id`) | SIEM / Victoria Metrics + alertmanager |
| **Key usage audit (KMS)** | необычное decrypt `pii.special` | Security |
| **Backup restore drill + проверка шифрования снимка** | «бэкап есть, но открытый» | ежеквартально |
| **Dependency / secret scan** (gitleaks и аналоги) | ключи в репозитории | CI fail |

## 5. Реестр программных и аппаратных средств

### 5.1. Программные

| Средство | Тип | Назначение в «Медикаменте» |
|----------|-----|----------------------------|
| HashiCorp Vault / cloud KMS (Yandex Lockbox / AWS KMS и т.п.) | secrets & keys | DEK/KEK, ротация, crypto-shredding |
| cert-manager + internal CA | PKI | TLS/mTLS сертификаты сервисов |
| API Gateway (Kong / Envoy / cloud GW) | perimeter | TLS termination, authN, rate limit, отказ IDOR-паттернов |
| Istio / Linkerd (service mesh) | east-west | mTLS между микросервисами |
| PostgreSQL + volume encryption | data store | CRM, schedule, lab metadata |
| Object storage + SSE | data store | медкарты, договоры |
| OAuth2/OIDC IdP (Keycloak и аналоги) | IAM | сотрудники и пациенты ЛК |
| OPA / Kyverno | policy | enforce encrypt & TLS |
| SIEM / Victoria Metrics + Alertmanager | monitoring | аудит и алерты доступа |
| gitleaks / Trivy / Checkov | CI security | секреты, misconfig, образы |
| 1С (server mode) + защищённый контур обмена | legacy bridge | бухгалтерия без файлового шаринга ПДн |
| ETL + anonymization toolkit | analytics | зоны озера raw→anonymized |

### 5.2. Аппаратные / платформенные

| Средство | Тип | Назначение |
|----------|-----|------------|
| **HSM** или cloud HSM-backed KMS | hardware key store | корневые ключи для `pii.special` и подписи audit |
| **TPM** на серверах/нодах (где on-prem) | device trust | привязка дисков/агентов |
| **ККМ / эквайринговый терминал** сертифицированного типа | payment HW | приём оплаты; канал только в Payment Gateway |
| **Сетевое сегментирование** (firewall / NSG / K8s NetworkPolicy) | network | изоляция clinical / payments / analytics |
| **Шифруемые диски СХД / cloud volumes** | storage HW/platform | at rest для всех контуров |
| **Резервная площадка / snapshot storage** с encryption | DR | зашифрованные копии вне офиса (отказ от единственного сервера в здании) |

## 6. Итоговая таблица (формат задания)

| Данные | В чём необходимость защиты | Инструменты защиты |
|--------|----------------------------|--------------------|
| ФИО, дата рождения | ПДн; идентификация субъекта; риск по 152-ФЗ и репутации | TLS; volume/TDE; маскирование в логах/UI; RBAC; тег `pii` |
| Телефон, e-mail | ПДн; канал социальной инженерии и спама | TLS; encrypt at rest; маскирование; минимизация в уведомлениях |
| Адрес, место работы/учёбы | ПДн; часто избыточны — риск при утечке анкет | encrypt rest+transit; Data Minimization; доступ need-to-know |
| Диагнозы, заключения, хронические заболевания | спецкатегория ПДн; максимальный ущерб пациенту | mTLS; field-level + HSM/KMS; ABAC; отдельный ключ; audit каждого доступа |
| Результаты анализов | спецкатегория; риск IDOR в ЛК и утечки реестров Excel As-Is | Lab API mTLS; encrypt DB/objects; ABAC «только свой patient_id»; тег `pii.special` |
| Договоры (сканы, номера) | ПДн + коммерческая тайна | SSE object storage; TLS; retention; запрет общей шары |
| Платёжные данные / чеки | финансы + связь с пациентом | токенизация; TLS к KKM/эквайрингу; Payments DB encrypt; сегмент сети; без Excel-дубля |
| Учётные записи, пароли, API-ключи | компрометация = доступ ко всем ПДн | Vault; хеш паролей; short-lived tokens; gitleaks в CI |
| Журналы аудита доступа | доказательная база инцидентов | append-only/WORM; encrypt rest; контроль целостности; алертинг |
| Данные ТМЦ | целостность учёта; не смешивать с clinical | volume encrypt; NetworkPolicy; RBAC warehouse; отдельный контур |
| Витрины Data Lake (analytics) | риск восстановления личности из «почти обезличенных» данных | ETL de-identify; зоны anonymized; запрет сырых ПДн аналитикам; audit выгрузок |
| Резервные копии всех контуров | полный снимок ПДн вне боевого периметра | backup encryption; отдельный KEK; drill восстановления; ограниченный доступ |

## 7. Связь с архитектурой Task2

- **KMS / Secrets** — центр ключей at rest / field-level.  
- **IAM / AuthZ** — кто может инициировать decrypt и видеть данные in use.  
- **Privacy & Consent** — класс и retention определяют обязательный уровень шифрования.  
- **Audit & Monitoring** — автоматизированный контроль decrypt и доступа.  
- **Analytics Platform** — вместо шифрования «всего озера как боевой БД» для BI используется обезличивание + жёсткий контроль raw-зоны.
