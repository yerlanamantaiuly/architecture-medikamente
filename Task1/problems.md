# Задание 1. Список проблемных зон и аудит безопасности данных

## 1. Контекст As-Is

Компания «Медикаменте» ведёт учёт пациентов, записей, медкарт, анализов и платежей преимущественно вручную: Excel/PDF/JPG на общем файловом диске, плюс «1С:Бухгалтерия» и «1С:Торговля и склад» в файловом режиме на одном Windows Server в офисе. Доменная аутентификация (AD) есть, но на уровне приложений и файлов нет политики доступа к ПДн, аудита операций и контроля потоков данных.

Исходная C4-диаграмма: `software-architect-pro.png` (корень репозитория).

## 2. Конфиденциальные данные, не учтённые во внутренних системах

Данные фактически обрабатываются, но не выделены как защищаемые сущности в IT-системах (нет каталога ПДн, меток, владельцев, сроков хранения):

| Категория | Где лежит сейчас | Почему «не учтена» |
|-----------|------------------|--------------------|
| ФИО, дата рождения, телефон, e-mail | `Patients.xlsx`, журналы врачей, папки пациентов | Нет реестра ПДн, нет классификации |
| Адрес, место работы/учёбы | расширенные анкеты в файлах карт | Не отделены от остальных файлов |
| Хронические заболевания, заключения | PDF/JPG в `Pacients/` | Спецкатегория ПДн без усиленных мер |
| Результаты анализов | Excel `RegistryByDate`, файлы карт | Нет контроля доступа «только свой пациент» |
| Данные платежей / чеки | KKM → 1С, дубли в Excel у кассиров | Двойной учёт вне контура контроля |
| Договоры с клиентами | файловый диск / почта Exchange | Нет политики хранения и удаления |
| Учётные записи сотрудников (AD) | Windows Server | Нет связи RBAC с доступом к медданным |

## 3. Аудит текущих мер безопасности

| Область | Что есть | Оценка |
|---------|----------|--------|
| Идентификация/аутентификация | AD / LDAP, доменные учётки | Частично: только вход в ОС/домен |
| Авторизация к данным | права на шары файлового сервера | Слабо: часто общие папки, нет ABAC/RBAC по пациенту |
| Шифрование at rest | не применяется к Excel/PDF на диске | Отсутствует |
| Шифрование in transit | локальная сеть; OLE/TCP к 1С и KKM без выделенного TLS-контура для ПДн | Недостаточно |
| Аудит доступа | нет журналирования чтения/изменения медкарт и Excel | Отсутствует |
| Data Lineage | потоки не документированы и не контролируются | Отсутствует |
| Data Minimization | собираются расширенные анкеты «на всякий случай» | Не соблюдается |
| Privacy by Design | системы росли вокруг файлов и 1С | Не заложено |
| Резервное копирование / удаление по запросу | неформализовано | Риск нарушения прав субъекта ПДн |
| Периметр | сервер в том же здании, один физический контур | SPOF + физический доступ |

## 4. Сопоставление процессов с требованиями и практиками

Практики: **Privacy by Design**, **Data Minimization**, **Data Lineage**, разделение обязанностей, RBAC/ABAC, шифрование, тегирование чувствительных данных, аудит (в духе требований к обработке ПДн в РФ / 152-ФЗ).

| Процесс | Требование / практика | Факт As-Is | Разрыв |
|---------|----------------------|------------|--------|
| Запись и учёт пациента | минимизация ПДн; контроль доступа | ресепшен пишет ФИО/телефон в общие Excel | избыточный доступ коллег; нет ролей |
| Ведение медкарты | спецкатегория ПДн; аудит; шифрование | PDF/JPG в папках на шаре | любой с доступом к диску может читать |
| Оплата | целостность платёжных данных; разделение учёта | Excel + KKM + 1С, ручной двойной ввод | риск ошибок и утечки реквизитов |
| Учёт ТМЦ | целостность; отделение от ПДн пациентов | OLE между 1С; на том же сервере | смешение контуров |
| Анализы из лаборатории | ограничение API/контрактов; запрет кросс-доступа пациентов | реестры Excel по датам на диске | нет API-контракта, нет изоляции субъектов |
| Почта / напоминания | защита канала передачи ПДн | Exchange без политики для ПДн в письмах | утечки через почту и вложения |

## 5. Проблемные зоны

1. **Хранение ПДн «рядом с пользователем»** — Excel и сканы на общем диске без шифрования и без разграничения «свой/чужой пациент».
2. **Отсутствие каталога и классификации данных** — нельзя централизованно применить политики защиты и сроки хранения.
3. **Нет Data Lineage** — неизвестно, кто куда скопировал карту/реестр (локальные копии, почта, флешки).
4. **Слабая авторизация** — доменный логин ≠ политика доступа к медданным (нет RBAC/ABAC на уровне приложения).
5. **Нет аудита** — невозможно расследовать инцидент и доказать факт доступа.
6. **Двойной ручной учёт платежей** — Excel у кассиров дублирует 1С, расширяет поверхность утечки.
7. **Интеграции без контракта безопасности** — лаборатория → файлы; KKM → 1С по OLE/TCP без явной модели доверия и минимизации полей.
8. **1С в файловом режиме на одном сервере** — ограниченная масштабируемость и единая точка отказа при росте ×5.
9. **Нет процедуры удаления/прекращения обработки** по запросу клиента (NFT безопасности из брифа).
10. **Смешение доменов** — медданные, платежи, ТМЦ и почта на одном контуре без сегментации.
11. **Отсутствие тегирования чувствительных данных** — нельзя автоматически блокировать утечки и проверять релизы.
12. **Неготовность к мобильному ЛК и партнёрским API** — без PbD «по умолчанию» каждую новую интеграцию придётся перевалидировать с нуля.

## 6. Что улучшить (направление, без реализации To-Be)

- Ввести единый каталог ПДн и механизм **тегирования** (см. `data-protection.md`).
- Разнести категории данных по доменам; доступ — RBAC + ABAC (атрибут «пациент_id / роль»).
- Убрать Excel как систему учёта; перевести записи, карты и анализы в сервисы с шифрованием at rest/in transit.
- Включить аудит доступа и алерты на аномалии; связать с мониторингом.
- Минимизировать поля в интеграциях (лаборатория, платежи); запретить «широкие» API-контракты.
- Формализовать сроки хранения и процесс «право на удаление / прекращение обработки».
- Сегментировать контуры: клинические данные / платежи / ТМЦ / аналитика (обезличенная).

Подробные способы защиты по типам данных, тегирование и контролы на потоках — в [`data-protection.md`](data-protection.md).  
Диаграммы потоков: файлы `dfd-*.drawio` в этой директории (страница **As-Is** и страница **Controls**).
