# Задание 1. Данные для защиты, тегирование и меры на потоках

## 1. Список данных для защиты

Способы: **шифрование** (at rest / in transit), **обфускация** (маскирование в UI/логах), **обезличивание** (для аналитики / озера данных).

| Данные | Чувствительность | Шифрование | Обфускация | Обезличивание | Комментарий |
|--------|------------------|------------|------------|---------------|-------------|
| ФИО | ПДн | да (rest + transit) | частично в логах/тикетах (`И***ов`) | токенизация / псевдоним для BI | идентификатор субъекта |
| Дата рождения | ПДн | да | возраст вместо даты в отчётах | обобщение (год/диапазон) | |
| Телефон, e-mail | ПДн | да | маскирование (`+7***1234`) | хэш/токен для рассылок | каналы уведомлений |
| Адрес прописки | ПДн | да | скрытие в ролях без нужды | агрегация до региона | |
| Место работы/учёбы | ПДн | да | — | исключать из аналитики по умолчанию | минимизация сбора |
| Хронические заболевания, диагнозы, заключения | спецкатегория | да (усиленно, отдельный ключ/HSM) | не показывать в чужих карточках | только после IRB-подобных правил / агрегаты | медданные |
| Результаты анализов | спецкатегория | да | в ЛК — только свои | деперсонализированные витрины | |
| Номер договора, скан договора | ПДн + коммерч. | да | — | — | сроки хранения |
| Платёжные данные / чеки | финансы + связь с пациентом | да (PCI-подобные практики для карты; в 1С — штатные средства) | маскирование в UI кассира | отрыв от ФИО в аналитике | |
| Данные ТМЦ | обычно не ПДн | по политике целостности | — | — | не смешивать с медкартами |
| Учётки сотрудников, роли | служебные | да (секреты, пароли — хеш) | — | — | основа RBAC |
| Логи доступа к картам | метаданные доступа | да | маскировать ПДн в текстах логов | — | сами логи — объект защиты |

## 2. Механизм тегирования данных

### Цель

Единообразно помечать чувствительность данных, чтобы политики доступа, шифрования, маскирования, запрета выгрузки и проверки релизов применялись автоматически (в т.ч. для будущего мобильного ЛК и партнёрских API).

### Модель тегов

Каждый элемент данных (поле, файл, таблица, сообщение в шине) получает набор тегов:

| Тег | Значение (пример) | Назначение |
|-----|-------------------|------------|
| `data.class` | `public` / `internal` / `pii` / `pii.special` / `payment` | класс конфиденциальности |
| `data.category` | `identity`, `contact`, `clinical`, `lab`, `billing`, `contract` | предметная категория |
| `data.subject` | `patient`, `employee`, `vendor` | чей субъект |
| `data.retention` | срок в днях / политика (`P3Y`, `legal_hold`) | хранение и удаление |
| `data.lineage` | id источника + id потока | происхождение |
| `data.masking` | `none` / `partial` / `full` | правило отображения |
| `data.encryption` | `rest`, `transit`, `field` | требуемый уровень |
| `data.legal.basis` | основание обработки | для аудита соответствия |

Пример: результат анализа  
`data.class=pii.special; data.category=lab; data.subject=patient; data.encryption=rest+transit+field; data.masking=full_for_non_owner`.

### Инструменты тегирования (предложение под стек компании)

| Слой | Инструмент / способ | Как используется |
|------|---------------------|------------------|
| Схема и контракты API | OpenAPI + расширения (`x-data-class`) / JSON Schema annotations | тег на поле контракта; gate на PR |
| СУБД (Postgres) | комментарии/колоночные labels + политика в приложении; при необходимости — column-level security | тег → правило RLS/ABAC |
| Файлы / объектное хранилище | object tags / metadata (S3-совместимые теги или аналог) | запрет публичных ACL на `pii*` |
| Потоки / шина | заголовки сообщений с тегами класса | фильтрация потребителей |
| Каталог данных | Data Catalog (OpenMetadata / DataHub / Apache Atlas) | единый реестр тегов и владельцев |
| Озеро / аналитика | теги в Glue-подобном каталоге + отдельные зоны `raw` / `curated` / `anonymized` | PbD для BI/ML |
| CI/CD | сканер схемы и diff контрактов (запрет снятия тега `pii.special` без approve) | «релиз проверяется на тегированные данные» из брифа |
| Мониторинг | алерты Victoria Metrics / SIEM по событиям доступа к тегам `pii*` | нетипичный доступ |

### Жизненный цикл тега

1. **Classify** — при создании поля/потока (вручную владелец домена + правила авто-классификации по имени/паттерну).  
2. **Enforce** — PEP (policy enforcement): API gateway, сервис авторизации, маскирование в UI.  
3. **Propagate** — тег копируется вместе с данными (lineage), при ETL — пересчёт (часто → обезличивание и смена `data.class`).  
4. **Audit** — любое чтение `pii` / `pii.special` пишется в audit log.  
5. **Retain/Delete** — job по `data.retention` и запросам субъекта.

## 3. Инструменты, способы и меры на потоках

Общие меры для всех процессов:

- TLS для всех внешних и межсервисных каналов; отказ от передачи ПДн по открытому OLE/файлам в To-Be.
- Шифрование дисков/томов + field-level для спецкатегорий (ключи в Vault/HSM).
- RBAC (роли: ресепшен, врач, кассир, бухгалтер, склад, пациент ЛК) + ABAC (`patient_id` / consent).
- Маскирование и запрет ПДн в логах приложений.
- Централизованный audit trail + алерты.
- Data Minimization в API (только нужные поля).
- Сегментация сетей/namespace в K8s: clinical / payments / analytics.

| Поток (процесс) | Меры на этапах |
|-----------------|----------------|
| Запись и учёт пациента | сбор минимума полей; шифрование БД; RBAC ресепшен; аудит create/update; тег `pii` на ФИО/телефон |
| Медкарта | отдельное хранилище клинических объектов; `pii.special`; доступ только лечащему контуру; шифрование; запрет шары Excel |
| Оплата | токенизация платежа; маскирование в UI; канал KKM→платёжный сервис по TLS; не дублировать ПДн в Excel |
| ТМЦ | изоляция от клинического контура; интеграция с бухгалтерией без передачи медкарт |
| Анализы / лаборатория | API-контракт с минимизацией; authN/authZ; запрет IDOR (пациент видит только свои); тег `lab` + lineage от лаборатории |

## 4. Связь с диаграммами

В каждом файле `dfd-0N-*.drawio`:

- страница **As-Is** — текущий поток без контролов;
- страница **Controls** — те же сущности с пометками мер (TLS, encrypt, RBAC/ABAC, mask, tag, audit, minimize) на стрелках и хранилищах.
