# Задание 5. Cutover-план миграции «Медикаменте»

## 1. Контекст

**As-Is:** Excel-журналы и карты на файловом диске, 1С (файловый режим), KKM↔1С по OLE/TCP, один сервер в офисе.

**To-Be:** Client/Staff Portal, CRM, Payment Gateway, Lab Integration, контур Privacy by Design (Task2); рост нагрузки до ×5, филиалы, ЛК пациента.

**Критичные процессы, которые нельзя останавливать надолго:** запись к врачу, доступ к медкарте, приём оплаты.

## 2. Выбор стратегии: Parallel run

Из трёх вариантов выбран **Parallel run** — параллельная работа старой и новой платформы с постепенным переводом нагрузки.

| Стратегия | Вердикт для «Медикаменте» |
|-----------|---------------------------|
| High-level design | Нужен как каркас доменов (уже в Task2), но сам по себе не даёт безопасного cutover операционных процессов |
| **Parallel run** | **Выбран:** клиника не может «встать» на день; можно сверять запись/оплату old vs new и откатываться по доменам |
| Branch by abstraction | Полезен внутри нового кода (anti-corruption к 1С/файлам), но при Excel-As-Is абстракция над шарой слабее, чем явный parallel run с dual-read/dual-write |

### Преимущества Parallel run здесь
- нулевой/минимальный простой для пациентов и ресепшена;
- сравнение метрик и данных до отключения Excel;
- поэтапный go-live: сначала запись, потом карты, потом оплата/лаборатория;
- понятный rollback: трафик и ввод возвращаются на As-Is.

### Ограничения
- стоимость двойной поддержки и риск **рассинхронизации** данных;
- нагрузка на маленькую IT-команду (3 чел.) — нужны чёткие роли и окно dual-run;
- дисциплина: запрет «теневых» правок только в Excel после перевода домена.

**Дополнение:** внутри новой платформы применяем элементы Branch by abstraction (порт к 1С/уведомлениям), но **управляющий сценарий cutover — Parallel run**.

## 3. Критические моменты

1. Старт dual-write «запись + пациенты» (риск расхождения журналов).  
2. Переключение ресепшена на Staff Portal как primary.  
3. Открытие Client Portal пациентам (пик нагрузки + IDOR/auth).  
4. Cutover оплаты (KKM → Payment Gateway) — деньги и чеки.  
5. Отключение Excel как source of truth (точка невозврата по домену).

## 5. Роли и ответственность (RACI, кратко)

| Роль | Зона |
|------|------|
| **Технический директор** | стратегия, go/no-go, флаги, архитектура, эскалация отката |
| **Администратор сети** | K8s/сеть/сертификаты, мониторинг, ACL, DNS |
| **Бизнес-аналитик** | качество данных, reconcile-отчёты, SLO бизнес-метрик |
| **Ресепшен-лид** | операционный ввод записей, UAT, сигнал о сбоях у стойки |
| **Кассир-лид + Бухгалтерия** | сверка платежей, допуск волны C |
| **Врач-лид** | приёмка карт и анализов, клинический UAT |
| **Руководство** | согласование окон cutover и коммуникации пациентам |

## 6. Управление рисками Parallel run

| Риск | Проявление | Меры |
|------|------------|------|
| Рассинхрон данных | Разные слоты в Excel и Portal | Dual-write + автоматический reconcile; конфликт → слот blocked до ручного разбора |
| Двойная нагрузка на людей | Ошибки ввода, обход процедур | Короткие волны; чеклисты; запрет правок «только в Excel» после primary=Portal |
| Расхождение денег | Чек есть, в 1С нет (или наоборот) | Дневная сверка; идемпотентные payment keys; стоп волны C |
| Деградация производительности | Медленный ЛК при canary | Perf до старта; HPA; canary 10%→50%→100%; алерты p95/error rate |
| Сбой Lab/KKM | Нет результатов / не проходит оплата | Таймауты, очереди, circuit breaker; runbook канала contingency |
| Нехватка IT | Затяжной dual-run | Фиксированный календарь волн; подряд на infra; единый war-room в дни cutover |
| Утечка ПДн в переходный период | Копии Excel + новая БД | Шифрование и ACL (Task3); аудит; минимизация выгрузок reconcile |

## 7. Блок-схема cutover (логический поток)

```text
[Подготовка + тесты]
        ↓
[Волна A: Запись/пациенты — Parallel run]
        ↓ go/no-go
[Волна B: Медкарты — Parallel run]
        ↓ go/no-go
[Волна C: Оплата — Parallel run]
        ↓ go/no-go
[Волна D: Лаборатория — Parallel run]
        ↓ go/no-go
[Стабилизация / мониторинг SLO]
        ↓
[Decommission Excel как SoT]
        ↓
(при провале любой волны → Откат primary на As-Is по runbook)
```

## 8. Итог

Для «Медикаменте» **Parallel run** — оптимальный cutover: клиника продолжает обслуживать пациентов, риски ловятся сверкой доменов, откат локален по волнам. Цена — дисциплина dual-run и контроль синхронизации; она заложена в этапы, роли и таблицу мер выше.
